## 원본을 실행한 방법

기준 실행 파일은 기존 포팅판에서 사용한 1.0.3 ARMv7이다. SHA-256은 `6ec47ea094abaa31bab10058fe47bb25d46c6038b2e88a7da2629899f84af112`이다. 지형 파일 `MapInfo.mcb`의 SHA-256은 `94799572dddde75ed235f297a4e716e9bbbce852f2b15953cc3e85912eb853d0`이며, 현재 프로젝트의 파일과 같다.

별도 iPhone Air 시뮬레이터 앱에 원본 포팅 런타임을 설치했다. 앱 식별자는 `com.gelb2.machdefense.audit.terrain20261106`이다. 이 앱 안에 `AUDIT` 프로필을 메모리로 만들었다. 사용자 아이폰·아이패드·갤럭시의 저장 파일은 사용하지 않았다.

touchHLE의 GDB 연결로 원본 함수에 입력을 주고 결과 메모리를 읽었다. 원본의 이동·충돌 함수를 반복 호출하는 검사 루프를 임시로 넣었다. 각 틱마다 원본 시간 증가량 `0.016599999740719795`초를 더했다. 검사 후 임시 루프가 차지했던 코드를 되돌렸다. 이동·충돌 함수와 지형 데이터는 바꾸지 않았다.

이동 검사에서는 전투와 렌더링을 실행하지 않고 아군 `aiMove` 또는 적 `processAI_Vehicle` 다음에 `processMove`를 호출했다. `processMove` 안에서 원본 보행·차량 이동, 지형 충돌, 같은 편 유닛 충돌이 실행된다. 600틱마다 좌표와 체력을 기록했고 각 조건은 12,000틱, 약 199.2초를 실행했다. 포팅 런타임에서 원본 ARMv7 코드를 실행한 결과다. 실제 화면을 손으로 조작한 플레이 검사는 별도로 남는다.

재개발판은 현재 C++ 코어를 Release로 빌드해 검사했다. 무기를 끄고 검사 대상 외 일반 유닛을 제거했다. 두 구현 모두 아이폰 기준 `deviceScale=0.5`, 월드 길이 1,024를 사용했다. 난수 소비 순서와 모든 내부 보행 상태를 두 구현 사이에서 일치시키지는 않았다. 따라서 출발 좌표가 같아도 경로가 달라질 수 있다.

## 미션 3: 구덩이에 포탑을 설치하는 원본 절차

미션 3 두 번째 통행 제한 다각형 안의 `(67,79)`를 골랐다. 원본 `DlgBuildMach::setAttackPos:`에 이 좌표를 전달했다.

1. 원본 생산 대기열이 0개에서 1개로 늘었다.
2. 대기열의 설치 좌표는 `(67,79)`, 생산 시간은 12초였다.
3. 원본 `BuildItem::tick`을 실행하자 `Tur_Gun_01`을 운반하는 type 5 봇이 생성됐다.
4. 봇은 `(66.5644,75.2040)`까지 이동했다. 원본 변환 처리는 최종 포탑을 `(67,79)`에 설치했다.
5. 포탑에 원본 이동·충돌 처리를 600틱 더 실행했다. 좌표 `(67,79)`, 체력 1,200을 유지했다.

재개발판도 `(67,79)` 주문을 받아 운반봇을 거쳐 체력 1,200의 `Tur_Gun_01`을 만들었다. 최종 좌표는 운반봇 도착점 `(66.5644,75.2040)`이었다. 설치가 허용된다는 결과는 같고, 최종 좌표는 약 3.82 월드 단위 다르다. 원본은 요청 좌표를, 현재 코어는 도착 좌표를 사용한다. 이 좌표 차이는 후속 대조 항목으로 남긴다.

이번 검사로 생산 대기열 수락·운반·설치·설치 뒤 위치를 확인했다. 설치된 포탑의 사격은 이번 조건에서 실행하지 않았다.

## 미션 4: 적 차량

`E_Tank_01`을 Y=280에서 출발시켰다. 체력은 원본 값 1,200을 사용했다.

| 시작 X | 원본 약 199초 뒤 좌표 | 재개발판 약 199초 뒤 좌표 |
| --- | --- | --- |
| -110 | (-53.97,101.80), 구덩이 위 정체 | (-52.07,-375.54), 통과 |
| -100 | (-35.20,-375.07), 통과 | (-54.92,102.38), 구덩이 위 정체 |
| -90 | (-54.63,-375.30), 통과 | (-46.20,-381.66), 통과 |
| -75 | (-87.63,-21.78), 통과 미완료 | (-118.38,35.98), 가장자리 정체 |
| -55 | (-117.67,35.74), 가장자리 정체 | (-49.79,-384.67), 통과 |

원본과 재개발판 모두 구덩이 위 Y≈102 및 왼쪽 가장자리 Y≈36에서 정체한다. 어느 출발 X가 그 위치에 도착하는지는 다르다. 각 차량의 목표 갱신에 쓰는 난수와 초기 조향 상태까지 맞춰야 이 차이의 원인을 좁힐 수 있다.

추가로 `(-55,100)`에서 바로 출발시키면 두 구현 모두 아래쪽으로 통과했다. 이 좌표에서 시작하는 것과 Y=280부터 내려와 그 근처에 도착하는 것은 조향·충돌 상태가 다르다.

## 미션 10·11: 메크

MachineGun의 기본 부품과 체력 300을 사용했다.

| 미션·출발 좌표 | 원본 12,000틱 뒤 | 현재 코어의 기존 탐침 |
| --- | --- | --- |
| 10, (-55,75) | (-4.94,369.32), 통과 | (-58.07,68.15), 정체 |
| 10, (-45,75) | (-5.74,368.56), 통과 | (-11.09,369.61), 통과 |
| 11, (35,-380) | (43.53,-379.95), 정체 | (42.01,-377.98), 정체 |
| 11, (55,-380) | (49.40,370.94), 통과 | (-2.35,370.67), 통과 |

기존 코어 탐침은 실제 생산으로 만들어진 메크의 위치와 이동 상태 일부만 바꿨다. 발 교대 단계·발 자세·몸체 각도 등은 생산 직후의 값이 남아 있었다. 미션 10 `(-55,75)` 조건에서 `BipodMotion` 전체를 초기화하고 보폭과 방향을 새 메크처럼 설정하자 `(-11.94,369.12)`까지 통과했다.

따라서 미션 10은 위치만 같은 검사로 원인을 확정할 수 없다. 사용자가 본 정체는 투두에 유지한다. 다음에는 같은 위치에 진입하는 순간의 발 교대 단계, 몸체·발 각도, 목표점, 현재 충돌선, 난수 상태를 함께 기록한다. 미션 11은 원본 실행에서도 정체 조건을 확인했다.

기존 조사에서 발견한 충돌선 등록 검사점 차이도 남아 있다. 원본 `addColVector:`는 마지막 검사점에 `(large,small)`을 다시 사용하고, 현재 코어는 `(small,large)`를 사용한다. 기존 사본 실험에서 이 점만 고쳐도 미션 10 정체는 남았다. 이번 결과도 이 차이 하나를 정체의 원인으로 확정하지 않는다.

## 밀집 포탑

지형 장애물이 없는 미션 1에서 `Tur_Gun_01` 다섯 대를 Y=0, X=-48/-24/0/24/48에 배치했다. 포탑 반경과 메크 반경은 각각 10이다. MachineGun은 `(0,-30)`에서 출발했다.

- 원본: 12,000틱 뒤 `(-12.13,-14.59)`. 중간 기록도 포탑 앞에서 움직였다.
- 재개발판: 12,000틱 뒤 `(12.31,-14.77)`. 포탑 열을 통과하지 못했다.

포탑 중심 간격은 24이며 양쪽 반경을 빼면 틈은 4다. 반경 10인 메크는 그 틈으로 통과할 수 없다. 양옆의 열린 길로 돌아가는 처리까지 확인하려면 포탑 간격 40 이상, 한쪽 끝이 열린 배열, 두 줄 배열을 따로 검사해야 한다. 현재 결과는 원본도 좁은 틈 앞에 오래 머물 수 있음을 보여준다.

## 재실행 자료

로컬 `.local/terrain-followup/`에 검사 도구와 결과를 보관했다.

- `run-original.py`, `rsp.py`, `cases.py`: 원본 런타임 연결·프로필 준비·배치·결과 수집.
- `move-loop.s`, `tick-loop.s`: 원본 함수를 호출하는 검사 루프. 해당 `.bin`은 이 짧은 검사 코드만 포함한다.
- `original-results.log`, `original-m*.json`, `original-dense-turrets.json`: 위 표의 원본 실행 결과.
- `current-reproduce.cpp`, `current-fresh.cpp`, `current-extra.cpp`, `current-m4-many.cpp`, `current-m3.cpp`: 현재 코어 대조.
- `current-*.csv`: 현재 코어의 틱별 좌표.

초기 실험인 `original-m10-initial.json`은 교전·소멸이 섞였고, `original-m10-isolated.json`은 시계를 600틱마다 바꿨다. 위 판정에서는 두 파일을 제외했다. 최종 검사는 매 틱 시계를 증가시키고 별도 앱을 재실행해 같은 결과를 다시 확인했다.
