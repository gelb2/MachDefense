# PWA 갱신·자원 검사 — 2026-11-07

작업 브랜치 `feat/pwa-tauri-followup-20261107`. 운영 배포 전 로컬 검사 결과다.

기존 시작 화면은 활성 워커의 자원을 준비한 뒤 새 워커를 비동기로 요청했다. 따라서 첫 실행에는 이전 표와 코드가 남을 수 있었다. 시작 화면에서 설치 상태를 기다리고, 다른 게임 창이 없으면 준비된 워커로 전환한 뒤 화면 코드까지 다시 읽도록 수정했다. 다른 창이 게임을 실행 중이면 기존 버전을 유지한다.

- 매니페스트를 워커 안에 고정했다. 배포 중 서로 다른 버전의 매니페스트와 코드가 섞이면 해시 검사에서 거절한다.
- 기존 파일·캐시 조각을 SHA-256과 길이로 검사한 뒤 재사용한다. 손상된 파일은 다시 받고, 실패한 업데이트는 기존 완성 버전을 유지한다.
- 66,614,478바이트 `game.data`를 원본 자원 16개 단위, 최대 4MiB씩 총 95조각으로 나눴다. 조각 URL에 내용 해시를 넣었다. 실행기에는 검증·재조립한 동일 바이트를 전달한다. C++·Apple·Android 파일은 이 작업에서 바꾸지 않았다.
- 조각과 완성 data 파일을 캐시에 중복 저장하지 않는다. 현재와 직전 빌드의 자원만 보존한다. 게임 진행 IndexedDB는 자원 정리 대상에 넣지 않는다.
- WebKit의 실패한 최초 설치를 재시도할 때 남은 캐시 핸들이 유효한 캐시와 어긋나는 현상을 재현했다. 실패한 첫 설치의 임시 자원 캐시를 정리하고 다시 설치하도록 수정했다.

## 검사

Chrome·WebKit에서 손상된 첫 설치, 정상 재시도, 실제 게임 시작, 실행 중 업데이트 대기, 다른 게임 탭이 있을 때 전환 보류, 첫 시작 화면의 새 버전 적용, 저장 유지, 손상된 업데이트의 이전 버전 유지, 캐시 손상 복구, 오프라인 게임 재실행을 확인했다.

data의 마지막 자원 일부를 바꾼 시험에서는 **72,193바이트 조각 한 개**만 받았다. 66.6MB 전체 파일은 다시 받지 않았다. 재조립 결과의 SHA-256도 기대값과 같았다. 변경 위치와 파일 목록에 따라 필요한 조각 수는 달라진다. wasm이 달라지면 wasm 파일을 다시 받는다.

[Chrome 결과](pwa-update-20261107/chrome.json) · [WebKit 결과](pwa-update-20261107/webkit.json). 검사 도구는 `Web/tests/update-integrity.mjs`다. 큰 바이너리를 숫자 배열로 자동화 프로세스에 복사하던 검사 코드가 메모리 한도에 걸려, 브라우저 안에서 해시를 계산해 비교하도록 고쳤다. 이 실패를 게임 크래시로 집계하지 않았다.

현재 운영 v0.5의 시작 화면에는 새 워커 전환 버튼/요청 코드가 없다. 이미 켜 둔 구버전 창이 새 설치를 붙잡고 있으면 해당 창을 닫아야 새 워커가 활성화된다. 새 시작 화면을 받은 이후의 갱신 경로는 위 검사로 확인했다. 최종 운영 배포 뒤 기존 설치에서 이 최초 전환을 다시 검사한다.

기술 근거: [Service Worker skipWaiting](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting), [clients](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/clients). 실행 중인 다른 게임 창을 강제로 새 워커로 바꾸지 않도록 적용했다.
