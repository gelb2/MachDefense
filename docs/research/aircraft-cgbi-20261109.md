# 헬기 PNG 처리와 원작 최적화 조사

2026-11-09. 원작의 파일·최적화·정의·조립·렌더링 절차가 기준이다. 현재 헬기 작업에서 그 절차의 준수와 시각·성능 동등성을 충분히 검증하지 않았다. [작업 경위와 책임](../evidence/aircraft-resource-process-incident-20261109.md)을 별도 기록했다. 이번에는 원본·현행 파일을 읽고 조사 자료를 작성했으며 게임 자원을 바꾸지 않았다.

## 확인한 파일 처리

원본 WeMade 1.0.3 IPA는 기존 SHA-256과 일치한다. 패키지 안의 PNG 948개 모두 `CgBI` 청크가 있다. 그중 `iCCP`는 622개, `gAMA`는 132개, `cHRM`은 668개다. Apple은 당시 Xcode가 앱 번들의 PNG를 iOS용으로 최적화하며, 이를 일반 PNG로 되돌리는 도구를 제공한다고 설명한다. 원본 파일의 CgBI를 단순 확장자 차이로 취급해서는 안 된다. [Apple QA1681](https://developer.apple.com/library/archive/qa/qa1681/_index.html), [당시 PNG 빌드 설정](https://developer.apple.com/library/archive/documentation/DeveloperTools/Reference/XcodeBuildSettingRef/1-Build_Setting_Reference/build_setting_ref.html).

`CgBI`는 PNG의 iOS용 인코딩 변형이다. `RGBA`는 색·알파 채널 구성을 뜻한다. 두 용어는 서로 배타적인 파일 종류가 아니다. 앞선 ‘CgBI 대신 RGBA’라는 설명만으로는 원본의 압축·채널·알파 처리와 현재 경로의 차이를 충분히 설명하지 못했다. 원작 샘플은 PNG 헤더상 8비트 RGBA이며, CgBI 압축 내부의 색은 BGRA 순서와 사전 곱셈 알파로 처리한다. 일반 PNG는 색과 알파를 분리해 저장한다. [PNG 규격의 알파 표현](https://www.w3.org/TR/png-3/#6AlphaRepresentation).

[자원 준비 코드](../../tools/prepare_resources.py)는 CgBI의 raw DEFLATE를 풀고 B/R 채널을 바꾼 뒤, RGB를 알파로 나누어 일반 RGBA PNG로 저장한다. 저장기는 `IHDR`·`IDAT`·`IEND`만 작성한다. 따라서 원본의 ICC·감마·색도 메타데이터는 이어지지 않는다. 이 처리는 최초 소스 재구현 커밋 `efc5d4a`부터 있으며 헬기 추가 이전에 원작 자원에도 적용됐다.

최근 아이폰 설치에 사용한 로컬 Release 앱의 적 탱크 차체·메크 몸체·헬기 4종 몸체, 총 6개를 읽었다. 모두 일반 PNG이고 현재 Resources와 바이트가 같다. **현재 확인한 설치 자원에서도 원작 그림은 이미 일반 PNG로 변환돼 있다.** 원본 CgBI와 헬기 PNG가 그대로 섞였다는 설명만으로 현행 앱 상태를 설명할 수 없다. 원작 최적화 경로를 바꾼 영향은 기존 유닛과 헬기 모두의 비교 과제다. [Release 자원 기록](../evidence/aircraft-cgbi-20261109/release-bundle.json).

## 일반 PNG를 사용한 경로와 검증 누락

| 확인한 선택 | 실제 기술적 역할 | 빠뜨린 확인 |
|---|---|---|
| 원작 CgBI를 일반 PNG로 변환 | 소스 빌드가 읽는 준비 자원 형식을 통일 | 원본 CoreGraphics 처리와 최종 색·알파·성능의 동등성 |
| 헬기 생성 그림을 ImageMagick으로 크롭·축소하고 `PNG32` 저장 | 편집 결과를 기존 Resources·stb 로더에 바로 연결 | 원작 최적화 단계, 게임 크기의 면별 명암·부분 알파, 압축·읽기 비용 |
| 공통 로더·조립 함수를 재사용 | 기존 표시·무장 호출 경로에 연결 | 파일 작성·정의 생성·부품 분리·실제 렌더링 전 절차의 일치 |
| 주색·도장을 처리하고 PNG에 반영 | 승인된 색상 처리를 설치 자원에 고정 | 색조 외에 금속면·접합부·가장자리의 질감과 원작 비교 |

소스에서 확인한 것은 기존 일반 PNG 준비·편집 경로에 헬기 출력을 맞춘 선택이다. **일반 PNG만 써야 하는 기술적 제약은 확인되지 않았다.** 현재 Apple·Android·웹의 stb 호출에는 CgBI 채널 변환과 알파 역산 옵션이 모두 들어 있다. ‘엔진이 CgBI를 읽을 수 없어서 불가피했다’는 이유를 제시할 근거가 없다. 편집·연결이 가능하다는 사실을 원작 절차 준수의 근거로 사용한 판단이 잘못됐다. 현재 로더가 CgBI를 읽는다는 사실도 원작의 전체 최적화 경로를 재현했다는 증거는 아니다.

참조: [헬기 포장](../../tools/pack_aircraft_approved.py), [스카웃 포장](../../tools/pack_scout_ah1z.sh), [도장 준비](../../tools/bake_aircraft_paint.py), [Apple 로더](../../Sources/Platform/Apple/MDRenderer.mm), [Android 로더](../../Android/app/src/main/cpp/Renderer.cpp), [웹 로더](../../Web/src/Renderer.cpp).

## 질감·색·경계가 달라질 수 있는 지점

| 지점 | 발생 가능한 변화 | 이번 확인 |
|---|---|---|
| B/R 채널 순서 | 적색·청색이 바뀌어 색조 왜곡 | 현재 변환과 stb 직접 해독의 샘플 결과가 같음 |
| 사전 곱셈 알파와 분리 알파 | 잘못된 조합이면 어두운 테두리, 과도한 밝기·투명도 | 현행 Sprite 기본은 분리 알파·`SRC_ALPHA`. 무조건 이중 곱셈한다고 확인한 것은 아님 |
| 알파 역산과 8비트 반올림 | 반투명 가장자리·얇은 부위의 RGB 차이. 투명 픽셀의 원래 색은 복구 불가 | 샘플을 다시 사전 곱셈하면 RGB 채널 최대 1 차이 |
| 보간 전후 알파 처리 | 경계의 색 번짐·검은 가장자리·두께 차이 | CPU의 인접 픽셀 중간점 모델에서 차이 확인. 실제 GPU 프레임의 측정값은 아님 |
| ICC·감마·색도 제거 | 프로필을 적용하는 원본 경로와 대비·중간톤·색이 달라질 가능성 | 메타데이터 제거 확인. 실제 색 변환량은 미측정 |
| 큰 생성 그림의 Lanczos 축소 | 얇은 선·볼트·판재 경계가 평균화되며 부드럽거나 납작하게 보일 가능성 | 포장 코드의 Lanczos 축소 확인. 같은 크기 원작과 시각 대조 필요 |
| NEAREST와 LINEAR 차이 | 픽셀 경계·회전 중 자글거림·세부 묘사 차이 | 원작 지상 파츠 기본 LINEAR, 비행 파츠 NEAREST 지정 확인 |
| 주색·회색화·톤 곡선 | 원래 색 대비와 면 구분이 변할 수 있음 | AH-10·샤이엔의 휘도 혼합과 중간톤 곡선 확인. 알파·외곽 보존만으로 질감 보존을 증명하지 못함 |
| 파츠·그림자·선회 묘사 | 합쳐진 몸체와 측면 부재로 입체감 감소 | 벨루가 별도 날개·엔진 미연결, 정면 이미지 기울임 확인 |

원작 `Texture2D::initWithImage`의 기존 분석 `0x4b590`에는 `CGImage`에서 정보를 읽고 `CGColorSpaceCreateDeviceRGB`·`CGBitmapContextCreate`·`CGContextDrawImage`를 거치는 경로가 있다. 현행은 stb 픽셀 해독 뒤 직접 업로드한다. ICC가 있는 원본을 해당 CoreGraphics 경로로 그렸을 때의 출력과 현재 stb 출력을 직접 비교해야 한다. 메타데이터가 제거됐다는 사실만으로 화면이 얼마나 변했다고 수치를 만들지 않는다. [기존 원본 분석](../evidence/module-work-20261105.md). PNG의 색상 프로필·감마 의미는 [PNG 색 관리 규정](https://www.w3.org/TR/png-3/#11iCCP)을 참고했다.

## 픽셀 검사 결과

[재현 도구](../../tools/audit_aircraft_cgbi.py)는 원본 패키지의 해시를 검사하고, 제품의 준비 코드 및 실제 stb 버전으로 비교한다. 원본 IPA·추출 이미지·실행 바이너리는 보고 사이트에 올리지 않았다. [검사 JSON](../evidence/aircraft-cgbi-20261109/audit.json).

| 이미지 | 부분 알파 픽셀 | 직접 CgBI 해독 vs 준비 PNG 차이 | 불투명 RGB·알파 변경 | 재사전곱셈 RGB 최대 차이 |
|---|---:|---:|---:|---:|
| 적 탱크 32 차체 | 2,464 | 0 | 0 | 1 |
| 적 탱크 32 포탑 | 1,280 | 0 | 0 | 1 |
| 메크 몸체 18 | 351 | 0 | 0 | 1 |
| 머신건 106 | 184 | 0 | 0 | 1 |
| 메크 발 타일 시트 | 2,479 | 0 | 0 | 1 |

헬기 28개도 제품 stb와 Python 해독 결과가 같다. 이는 **현재 디코더에서 픽셀을 읽는 단계의 검사**다. 원작 CoreGraphics 출력, GPU 보간·합성, 기체 입체감, 실제 iPhone 성능의 동등성을 검증한 결과가 아니다.

검은 배경에서 가로로 붙은 두 픽셀의 중간점을 계산한 CPU 모델에서는 ‘분리 RGB와 알파를 각각 보간한 뒤 곱함’과 ‘사전 곱셈 RGB를 보간함’의 차이가 샘플별 최대 36.27~63.75/255였다. 일부 경계 픽셀의 이론 비교이며 화면 전체 오차율이나 실기기 측정값으로 사용하지 않는다. 규격 설명과 산술 모델을 원작 실제 GPU 결과로 대체하지 않는다.

첫 ICC 조사 실행은 iCCP에 일반 zlib 래퍼가 있다고 가정해 해독 오류가 났다. 해당 CgBI 샘플의 프로필 데이터는 raw DEFLATE로 해독됐고, 이 차이를 도구에 반영해 다시 검사했다. 실패를 파일 무결성 문제로 단정하지 않았다.

## CPU·메모리·프레임 영향

원작의 iOS 최적화는 검사 대상이다. 압축 형식·압축률·채널 순서·알파 방식이 바뀌면 **파일 읽기와 해독·변환 비용**이 달라질 수 있다. 최초 생산·첫 표시에서 이 처리가 실행되면 프레임 지연으로 이어질 수 있다. 현재 로더에는 이미지별 캐시가 있으므로 이미 준비한 그림을 매 프레임 PNG 해독하는 구조는 아니다. 캐시 존재만으로 최초 지연·다량 생산·복구 시 부하가 없다고 결론 내리지 않는다.

GPU에는 현재 RGBA 픽셀이 업로드된다. 같은 크기·픽셀 형식이라면 PNG 압축 파일의 크기가 GPU 텍스처 크기를 정하지 않는다. 실제 비용에는 2의 거듭제곱 패딩, 같은 그림의 알파 방식별 캐시, 파츠·그림자 그리기 횟수, 겹친 반투명 면적, 선회 메시 계산, 입자와 메모리 업로드가 포함된다.

현행 조립이 참조하는 헬기 고유 PNG 17개의 파일 합은 100,571바이트다. 해독 RGBA 합은 235,356바이트, 현재 패딩 규칙으로 이미지당 한 텍스처를 만든 계산값은 574,464바이트다. 전체 헬기 PNG 28개 파일 합은 223,858바이트다. **계산값이며 GPU 실측·전체 앱 메모리가 아니다.** 캐시 변형·드라이버 비용은 포함하지 않았다. [파일·메모리 계산표](../evidence/aircraft-cgbi-20261109/texture-budget.json).

기존 40·100기 웹 검사에서 장시간 프레임 사례와 재측정 결과를 기록했지만, 그것은 CgBI/일반 PNG·원작 최적화 경로를 같은 조건으로 비교한 실험이 아니다. 이를 포맷 선택의 성능 근거로 사용하지 않는다. 현재 iPhone에서 원작 최적화와 헬기 처리의 CPU·GPU·프레임 차이는 아직 분리 계측하지 않았다. **성능에 영향이 없다고 보고하지 않으며, 아직 측정하지 않은 저하량도 사실로 만들지 않는다.**

## 다음 검사와 기준

원작의 파일 준비·최적화·로딩·조립·렌더링 절차를 기준으로 헬기 전용 복원안을 작성한다. 최초 로딩·첫 생산·자원 준비 후 전투·컨텍스트 복구를 나눠 CPU 시간, 업로드, 메모리, p50/p95/p99·최대 프레임 시간을 측정한다. 같은 기기·배율·기체 수·화면 점유율에서 1·4·40·100기를 비교한다. 원본 제작 파일이 없는 부분은 확인 가능한 원작 자원·코드·실행 결과를 근거로 정리하고 임의의 절차를 원작이라고 부르지 않는다.

`MD-AIRCRAFT-CGBI-PERF-01`, `MD-AIRCRAFT-ASSET-PARITY-01`, `MD-AIRCRAFT-DEPTH-01`, `MD-AIRCRAFT-TURN-ASSETS-01`과 C++ 전체를 대상으로 한 `MD-AIRCRAFT-LOGIC-AUDIT-01`을 연결했다. 검사·수정·승인 범위를 구분하고 원작 유닛 코드·에셋은 보존한다.
