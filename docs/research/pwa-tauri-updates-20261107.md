# PWA와 Tauri Mac의 배포·업데이트

2026-11-07 후속 구현: PWA의 해시 검증·변경 자원 재사용·95개 자원 조각·시작 화면 전환을 구현했다. Tauri Mac의 파일 저장·복원·종료와 공식 updater도 구현했다. [PWA 검사](../evidence/pwa-update-20261107.md), [Tauri 검사](../evidence/tauri-desktop-20261107.md).

아래는 v0.5 당시 조사와 구현 순서다. 당시 미구현 항목의 현재 상태는 위 검사 기록과 [TODO](../usability-todo.md)를 따른다.

## 현재 PWA

`Distribution/Web/sw.js`는 다운로드한 각 파일의 SHA-256을 `asset-manifest.json`과 비교한다. 버전마다 별도 캐시를 만들고 활성화 때 이전 캐시를 지운다. 저장 데이터는 별도 IndexedDB에 있다.

현재 방식에는 다음 보강이 필요하다.

- 새 캐시는 이전 캐시의 동일 파일을 재사용하지 않는다. 코드·그림 한 부분만 바뀌어도 새 버전 자원을 다시 받는다.
- 캐시에 이미 있던 파일은 다시 해시를 계산하지 않는다. 캐시가 없는 파일의 일반 fetch 경로도 설치 때와 같은 검증을 거치지 않는다.
- 서비스 워커의 버전과 내려받은 매니페스트의 버전을 묶어 검사해야 한다. 배포 중 서로 다른 버전의 파일이 섞이지 않아야 한다.
- 실행 중인 이전 워커와 새 워커의 대기·전환 시점을 화면에 연결해야 한다. 전투 도중 교체하지 않고 시작 화면에서 완전한 새 빌드로 전환한다.

v0.5 산출물은 `game.data` 66,614,478바이트, `game.wasm` 1,236,233바이트다. 그림·음향·표는 한 개의 data 파일에 들어간다. PNG 하나를 바꿔도 이 묶음의 해시가 바뀐다. C++ 수정은 컴파일된 wasm을 바꾸므로 C++ 원문 몇 줄만 기기에 보내는 방식은 적용할 수 없다.

## 변경 파일만 받는 순서

1. 경로·크기·SHA-256이 있는 매니페스트를 하나의 릴리스에 고정한다. 클라이언트는 자기 실행 버전을 끝까지 사용한다.
2. 내용 해시가 같은 기존 파일을 재사용한다. 없는 파일만 임시 저장소로 받고 크기와 해시를 확인한다.
3. 필요한 파일을 모두 검증한 뒤 새 버전을 준비 완료로 표시한다. 다음 시작 화면에서 전환하고, 실패하면 기존 버전으로 계속 실행한다.
4. 이전 창이 쓰는 캐시와 최근 정상 빌드는 바로 지우지 않는다. 게임 저장 DB는 자원 캐시 정리 대상에서 제외한다.
5. 자원 묶음을 이미지·음향·표 또는 크기가 제한된 여러 묶음으로 나눈다. 패키지 수에 따른 요청 비용과 실제 업데이트 다운로드량을 측정해 결정한다. 파일 수천 개를 무조건 개별 요청하지 않는다.

Workbox precaching은 revision을 비교해 변경된 파일만 가져오는 방식을 제공한다. 현재 워커를 보강할지 Workbox를 도입할지는 작은 시험 배포로 비교한다. Emscripten은 file_packager를 통한 여러 자원 패키지를 지원하므로 공용 전투 코드를 바꾸지 않고 Web의 빌드·로더에서 분할할 수 있다. [Workbox precaching](https://developer.chrome.com/docs/workbox/modules/workbox-precaching), [Emscripten 파일 포장](https://emscripten.org/docs/porting/files/packaging_files.html).

매니페스트는 재검증하고, 해시가 포함된 자원 URL은 오래 캐시할 수 있게 구성한다. ETag는 변경 여부 확인에 쓰고 SHA-256은 받은 바이트 검사에 쓴다. `no-cache`는 매번 재검증하라는 뜻이며 저장 자체를 금지하는 `no-store`와 다르다. 실제 GitHub Pages 응답 헤더를 확인한 뒤 가능한 설정을 적용한다. [HTTP 캐시](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching).

새 워커의 대기 상태를 감지해 업데이트 안내를 표시하고, 저장 완료 후 시작 화면에서 적용한다. 다운로드 중 연결이 끊기면 다음 접속 때 재시도한다. [서비스 워커 업데이트 처리](https://developer.chrome.com/docs/workbox/handling-service-worker-updates).

## Tauri Mac 구성

HeavyMach의 `Desktop/Tauri`는 기존 웹 산출물을 별도 폴더에 복사해 실행한다. MachDefense도 같은 구조를 따른다. `Desktop/Tauri`에 Rust 호스트·설정·웹 산출물 준비 스크립트를 두며 Apple·Android 폴더에 Tauri 파일을 넣지 않는다. 게임은 현재 C++20·WebAssembly·WebGL2 실행기를 사용한다. Mac arm64를 대상으로 한다.

첫 구현은 다음 범위로 나눈다.

- 웹 게임 산출물을 앱에 포함해 최초 실행부터 오프라인으로 시작한다. Tauri에는 웹용 서비스 워커를 등록하지 않는다.
- 현재 MachDefense 저장 포맷과 MD1 복원 모듈을 그대로 사용한다. OS 앱 데이터 폴더의 파일을 임시 쓰기·검증·원자적 교체·백업 순서로 저장한다. HeavyMach의 저장 포맷을 복사하지 않는다.
- 저장 브리지를 붙일 때 비동기 파일 완료와 게임의 저장 완료 응답을 연결한다. 저장 중 창 닫기·Cmd+Q·메뉴 Quit도 확인한다.
- 앱 ID를 고정하고 기존 저장을 업데이트 후에도 읽는다. 키보드·트랙패드·음향·백그라운드 복귀·복원 코드를 실제 WKWebView에서 검사한다.
- Apple·Android·공용 Core의 파일 해시를 전후 대조한다. 브리지에 필요한 공용 API 변경이 발견되면 해당 변경과 영향부터 별도 기록한다.

## Tauri 업데이트는 두 층으로 나눈다

Tauri 공식 updater는 서명된 업데이트 패키지를 내려받아 설치한다. Mac은 `.app.tar.gz`를 사용한다. 기본 기능이 변경된 PNG나 wasm 조각만 받는 것은 아니다. 초기 구현은 공식 updater와 GitHub Release의 정적 JSON·서명 파일을 사용한다. 별도 서버는 필요하지 않다. 업데이트 서명 키와 검증용 공개키를 준비해야 하며 비밀키는 저장소에 넣지 않는다. [Tauri updater](https://v2.tauri.app/plugin/updater/).

Apple Developer ID 서명·공증은 업데이트 패키지의 서명과 별개다. 다운로드한 앱의 macOS 실행 안내도 실제 배포 서명 상태에 맞춰 작성한다. [macOS 서명과 공증](https://v2.tauri.app/distribute/sign/macos/).

나중에 큰 자원만 자주 바뀐다면 별도 자원 묶음을 앱 데이터 폴더에 두고 서명된 매니페스트로 검증하는 방식을 검토한다. 앱 번들 내부를 직접 덮어쓰지 않는다. 내려받은 JS·wasm에 네이티브 권한이 연결되므로 해시만으로 발행자를 신뢰하지 않고 매니페스트 서명과 허용 IPC도 함께 설계해야 한다. 이 방식은 공식 updater 외에 구현·검사가 더 필요하다.

Mac 전용 Sparkle은 구버전별 delta 업데이트를 지원하고 실패하면 전체 패키지로 대체한다. 다만 별도 Mac 프레임워크 연결이 필요하므로 현재 Tauri 공통 배포의 첫 선택으로 확정하지 않는다. [Sparkle delta 업데이트](https://sparkle-project.org/documentation/delta-updates/).

## 구현 순서와 검사

1. PWA에서 구버전·신버전 매니페스트 혼합, 다운로드 중단, 손상 파일, 캐시 누락을 재현한다. 기존 저장과 실행 가능한 이전 빌드가 남는지 확인한다.
2. 파일 해시 재사용과 완전한 빌드 전환을 구현한다. 변경 없는 업데이트는 자원 다운로드 0바이트, 한 파일 변경은 해당 묶음만 내려받는지 요청 로그로 확인한다.
3. 자원 분할 전후에 첫 설치 시간·업데이트 바이트·최고 메모리·오프라인 재실행을 비교한다. Chrome·WebKit와 실제 모바일 PWA에서 검사한다.
4. Tauri Mac을 현재 정상 웹 산출물로 빌드한다. 새 프로필과 실제 진행도를 각각 복원하고 앱 종료·강제 종료·재실행·업데이트 전후 저장을 비교한다.
5. 서명된 앱 업데이트를 검증한다. 잘못된 서명·구버전 설치·디스크 부족·네트워크 중단·업데이트 후 실행 실패도 검사한다.

현재 v0.5에는 기존 워커를 사용한다. 위 절차와 Tauri 앱은 후속 구현 대상이다. [TODO](../usability-todo.md) · [웹·복원·Tauri 설계](../save-transfer-web-tauri-plan.md).
