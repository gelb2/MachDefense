## 사용자 확인 — 설치된 유닛 전체를 스크롤

2026-11-06 사용자 승인: “hud는 그 계획대로 간다.” 기존 INSTALL·UNINSTALL과 설치 상태를 유지한다. HUD에는 `onSlot=true`인 유닛 전체만 표시하고, 스크롤로 찾아 기존 절차대로 생산한다. UNINSTALL한 유닛은 HUD에서 빠지며, 다시 INSTALL하면 목록에 들어온다. 해금됐다는 이유만으로 모든 유닛을 강제로 설치하거나 표시하지 않는다.

원작의 설치 개수 7개 상한과 HUD 표시 7개 상한을 풀되, 설치·해제 기능 자체와 생산 대기열 제한은 유지한다. 가격표·아이콘·받침 틀·효과와 터치 영역을 같은 행으로 옮긴다. 순서 편집은 설치 여부를 변경하지 않는다.

## 원작에도 7개 제한이 있다

원작은 생산 목록에 설치한 유닛을 최대 7개 표시한다. 장비 창도 7개를 설치하면 추가 설치 버튼을 비활성화한다. 보유 유닛 자체의 저장 공간은 7개보다 크다. 따라서 전체 해금 유닛에 접근하려면 표시 개수와 설치 조건을 함께 바꿔야 한다.

원본 실행 파일의 로컬 REA 분석과 현재 소스를 대조했다. 이번 조사에서는 포팅판에서 여덟 번째 유닛을 직접 설치하는 화면 검사를 추가로 수행하지 않았다.

| 원본 함수 | 확인한 처리 | 새 소스의 대응 |
|---|---|---|
| `DlgBuildMach::refreshButtonsWithType:` `0x2e090` | 합성 이미지와 터치 버튼 모두 7개에서 멈춘다. 어셈블리 `0x2e27e`의 `cmp r1,#6`과 다음 분기에서 첫 반복의 상한을 확인했다. | `GameHUD::configure`, `append`의 `min(7, production.size())` |
| `DlgUpgradeItem::initWithBuildSet:` `0x388a8` | 설치 버튼 `0x401`을 만들고 `buildBtnCnt < 7`일 때만 활성화한다. 비교 명령은 `0x39f1e`에 있다. | `GameSession::refreshUpgrades`의 `canInstall`, `action`의 설치 개수 검사 |
| `DlgBuildMach::installMach:` `0x2f580` | `onSlot`을 켜고 생산·장비 목록을 새로 만든다. 함수 자체에서 다시 7개를 세지는 않는다. | `GameSession::action`의 `0x401` |
| `DlgUpgradeEquip::refreshMachButtons` `0x36a84` | 보유 목록을 여러 행으로 만든다. 생산 HUD의 7개 제한과 구별된다. | 장비·강화 목록 |
| `GlobalInfo::saveDataFile` `0x1b5ac` | 보유 목록 순서대로 40바이트 레코드를 저장한다. | `SaveData::setBuilds` |
| `GlobalInfo::selectSlot:` `0x1a7c0`, `buyBuildSet:` `0x1d400` | 읽은 유닛을 종류·비용 조건으로 다시 삽입한다. 원작은 저장 레코드 순서를 임의 편집 순서로 그대로 사용하지 않는다. | 현재 `SaveData::builds`는 레코드 순서를 유지한다. 새 해금 때 `Settlement::addBuild`가 삽입 위치를 정한다. |

**생산 대기열의 7개 제한은 별도 규칙이다.** `GameSession::refreshHUD`가 대기열 길이로 생산 가능 여부를 계산하는 조건은 이번 목록 확장에서 유지한다. 필살기 목록·부대 대형의 개수도 이 과제에서 바꾸지 않는다.

## 무엇을 함께 움직일 것인가

원작은 `ImageAttacher`로 생산 패널과 각 유닛의 표시를 합성했다. 새 구현은 같은 자원을 C++ `Frame`에 순서대로 넣는다. 현재 이미 행별로 분리되어 있어 큰 HUD 이미지를 다시 자를 필요가 없다.

| 행에 포함할 표시 | 자원 또는 현재 처리 |
|---|---|
| 유닛 뒤 바탕과 금속 틀·가격 탭 | `Btn_BuildMachBG.png`, `Btn_BuildMach.png` |
| 유닛 자체 | 기존 `DrawMachine`의 부품 조립 스프라이트 |
| 생산 가격·영문 이름 | 기존 글꼴과 텍스트 배치 |
| 강화 레벨·강화 가격·강화 표시 | `Btn_BuildMachUpgrade.png`, `Btn_BuildMachUpgradeOn.png`, 기존 숫자 |
| 생산 수량 표시 | `Btn_BuildMachInd.png` |
| 누르는 동안의 빛·생산 불가 덮개 | `SelMach.png`, `BuildMach_Cover.png` |

이들을 한 행으로 묶고 동일한 Y 이동량과 자르기 사각형을 적용한다. 유닛 부품만 움직이거나 가격표만 남는 구현을 피한다.

다음 요소는 고정한다.

- `GameUI_MachSlot.png`의 금속 패널과 셀 표시 영역.
- 하단 주 HUD, 생산·스킬·지원 버튼, 메뉴와 기지 강화 버튼.
- 장비·강화 목록을 여는 `Btn_UpgradeEquip.png`.
- 월드, 미니맵, 생산 대기열, 기지 체력 표시.
- 사용자가 확인한 iPhone 상단 덮개와 현재 iPad 외형.

## 스크롤 영역과 검은 빈 공간 처리

원래 행 간격은 논리 좌표 51이다. 첫 유닛 중심은 `(292, 52)`, 금속 틀은 `(250.5, 28.5, 64, 64)`에 놓인다. 강화 표시의 왼쪽 끝은 237.5까지 나온다. 아이콘 폭만으로 잘라서는 가격·강화 표시가 잘린다.

설계는 다음과 같다.

1. 고정 패널을 현재 코드와 같은 위치·순서로 먼저 그린다.
2. 행 전체를 임시 `Frame` 또는 시작·끝 인덱스로 묶는다. 해당 행의 모든 스프라이트에 같은 스크롤 이동량을 적용한다.
3. 목록의 위쪽은 첫 금속 틀 상단을 기준으로 정한다. 아래쪽은 고정 장비 버튼 위를 기준으로 정한다. 최초 후보는 화면 좌표에서 `topRight.y + 28.5`부터 `bottomRight.y + 390`까지다. 자르기 폭은 가격·강화 표시를 포함하는 기존 패널 영역을 사용한다.
4. 아래쪽 행이 일부 보이면 사용자가 더 내릴 수 있음을 알 수 있다. 마지막 행을 끝까지 올렸을 때 가격표·기체·이름·틀 전체가 보이도록 최대 스크롤을 행의 전체 경계로 계산한다.
5. 위아래 이동 범위를 즉시 제한한다. 처음 구현에는 탄성 이동과 관성 이동을 넣지 않는다. 끝을 지나 빈 목록 공간이 드러나는 동작을 막는다.
6. 패널 뒤를 검은 사각형으로 채우지 않는다. 기존 금속 패널과 현재의 하단 연장 조각을 고정해 둔다. 투명한 부분에는 원래 월드가 보인다.
7. 목록 밖의 행은 출력과 입력 양쪽에서 제외한다. 화면 아래 숨은 유닛이 메뉴 버튼 터치로 생산되지 않도록 한다.

위 경계값은 구현 시작값이다. 첫 행의 가격 탭, 마지막 행과 장비 버튼의 겹침을 실제 렌더로 확인한 뒤 확정한다. 숫자만으로 시안을 승인한 것으로 처리하지 않는다.

`Sprite.clip`과 `glScissor`는 이미 Apple·Android·Web 렌더러에 있다. `FrameLayout::translateFrame`도 스프라이트와 자르기 사각형을 함께 옮긴다. 현재 유닛 미리보기는 부품 스프라이트를 출력한다. 행의 모든 출력이 스프라이트인 것을 검사하면 기존 렌더러를 그대로 사용할 수 있다. `TextureMesh`에는 같은 자르기 필드가 없으므로, 후속 변경에서 행에 메시를 넣을 때는 별도 대응이 필요하다.

## 스크롤과 생산 터치를 구별한다

현재 `Button`은 눌렀다 놓은 위치가 버튼 안이면 동작한다. 행 위치만 옮기면 드래그 끝에서 다른 유닛을 생산할 수 있다. 목록이 터치의 시작부터 종료까지 소유해야 한다.

- 손가락을 댈 때 터치 ID, 최초 좌표, 스크롤 위치, 유닛 이름을 저장한다.
- 정한 이동 문턱을 넘기 전에는 누름 효과를 표시한다. 문턱의 초깃값은 논리 좌표 6으로 두고 폰·패드에서 조정한다.
- 세로 이동이 문턱을 넘으면 기존 버튼 누름을 취소하고 스크롤로 전환한다. 손을 떼도 생산 액션을 내보내지 않는다.
- 짧게 누르고 같은 유닛 위에서 떼었을 때만 기존 생산·강화 액션을 한 번 전달한다.
- 목록에서 시작한 드래그가 월드로 넘어가도 월드 이동이나 포탑 배치로 전달하지 않는다. 월드에서 시작한 터치도 목록 스크롤로 바꾸지 않는다.
- 화면 전환·일시정지·레이아웃 변경·목록 내용 변경 때 잡고 있던 터치를 취소한다.
- 활성 손가락 이외의 두 번째 터치는 목록 상태를 바꾸지 못하게 한다. 남은 게임 터치의 허용 범위는 기존 입력 처리와 함께 검사한다.

현재 `setState`는 목록 개수가 같으면 버튼을 재구성하지 않는다. 순서 변경을 지원하려면 개수뿐 아니라 **유닛 이름의 순서**를 비교해야 한다. 액션 처리 직전에 행 번호와 유닛 이름을 다시 대조해, 해금·제거·강화 직후 다른 유닛이 생산되는 문제를 막는다.

## 설치된 유닛 전체에 접근하는 방법

설치 개수 상한을 없애고 설치한 전체 목록을 스크롤한다. 이미 사용자가 빼 둔 `onSlot=false` 유닛은 그대로 보존하며, 장비 창에서 추가 설치할 수 있게 한다. 기존 세이브를 불러오자마자 모든 설치 상태를 바꾸지는 않는다.

새 해금 때의 설치 정책을 스크롤 편의 때문에 별도로 바꾸지 않는다. 기존 해금 절차와 수동 INSTALL·UNINSTALL을 대조하고, 7개 상한 해제에 필요한 조건만 수정한다. 기존 저장의 설치 여부, 해금·가격·강화·생산 조건은 유지한다.

처음부터 모든 보유 유닛을 설치 상태와 관계없이 표시하는 방식은 기존 선택을 무시한다. 전체 목록을 볼 수 있게 하는 기능과 기존 설치 선택을 보존하는 기능을 함께 제공하는 쪽이 적합하다.

## 순서 편집과 저장

전투 중 같은 목록에서 드래그를 생산·스크롤·순서 편집 세 가지로 해석하면 오입력이 생기기 쉽다. **장비 화면에 명시적인 순서 편집 상태를 추가**하는 방식을 제안한다. 게임 버튼·원작 글꼴로 `ORDER`, `DONE`, `CANCEL`을 표시한다. 이 상태에서는 유닛 카드 전체를 움직이고 구매·강화를 실행하지 않는다. 완료할 때 한 번 저장하며 취소하면 순서를 되돌린다. 전투 시간이 흐르는 화면에서 편집한다면 기존 일시정지 처리도 함께 연결한다.

현재 저장 파일은 42,496바이트이며 슬롯은 5개다. 슬롯별 보유 유닛은 최대 128레코드를 담고, 각 레코드는 40바이트다. `onSlot`, 이름, 강화 레벨과 해석하지 않은 바이트가 있다. 복원 코드는 파일 전체를 운반한다.

### 제안 A: 기존 보유 레코드의 순서 사용

현재 앱은 보유 레코드 순서로 생산 목록을 구성한다. 이 순서를 편집 순서로 쓰면 별도 설정 파일이나 복원 코드 버전을 만들 필요가 없다.

다만 `setBuilds`로 값을 다시 조립해 순서를 바꾸면 레코드 안의 해석하지 않은 바이트가 원래 유닛과 함께 이동하지 않는다. 따라서 **40바이트 레코드 전체를 순열대로 옮기는 전용 함수**가 필요하다. 대상 슬롯의 보유 목록 범위만 바꾸고 나머지 슬롯·진척·자금·강화·필살기 데이터를 그대로 둔다.

원작 `buyBuildSet:`는 로드할 때 종류·비용으로 다시 삽입하므로, 편집 순서를 원작 포팅판까지 유지하는 것은 이 방식으로 보장할 수 없다. 새 iOS·Android·Web/PWA는 같은 코어로 순서를 유지할 수 있다. 기존 출시판은 7개만 보여도 목록 레코드는 읽을 수 있다.

새 유닛 해금 시 기존 사용자 순서를 보존하는 정책도 필요하다. 기존 원소의 상대 순서는 유지하고 새 유닛만 끝에 넣는 방법이 가장 명확하다. 현재 해금 함수는 종류·가격에 따라 중간에 삽입하므로 이 부분은 별도 동작 변경이다.

### 대안 B: 별도 표시 순서 저장

원본 보유 목록을 그대로 두고 유닛 이름 배열을 별도 설정으로 저장할 수도 있다. 그러나 모든 플랫폼의 저장·복원에 새 배열을 추가해야 하며, 기존 복원 코드와의 버전 처리도 필요하다. 이번 조사에서 이 확장 저장 형식을 확정하거나 적용하지 않았다.

우선 스크롤을 구현·검사하고 순서 저장은 독립 커밋으로 진행하는 것이 적합하다. A안을 채택해도 슬롯 개수·크기·이름·레벨 필드를 바꿀 필요는 없다. 저장 실패 시 편집 전 순서로 되돌리는 처리를 기존 저장 경로와 연결한다.

공용 C++ 코드에서 구현하므로 iPhone·iPad·Android·Web/PWA가 같은 동작을 사용한다. 플랫폼별 게임 버튼을 추가하지 않는다. 현재 스프라이트 자르기를 쓰는 범위에서는 Apple·Android·Web 렌더러 수정도 필요하지 않다.

피해 계산, 이동·길찾기, 사거리, 자연 생산 속도, 무장·음향에는 수정 이유가 없다. 생산 대기열의 제한과 비용 차감도 그대로 호출한다.

## 구현 후 검사

1. **현재 화면 보존:** 목록 1개·7개에서 기존 주 HUD·셀·장비 버튼·미니맵·월드 스프라이트를 기준 출력과 비교한다. iPhone 상단 덮개와 iPad 패널 위치도 비교한다.
2. **목록 접근:** 8개·12개·보유 유닛 전체를 INSTALL한 상태를 만들고 맨 위부터 맨 아래까지 모든 이름·가격·틀이 함께 보이는지 검사한다. 처음·끝을 넘는 드래그에서도 검은 빈 영역이 생기지 않아야 한다.
3. **행 출력:** 부품·글자·가격표·딤·글로우 모두 같은 이동량과 동일한 clip을 갖는지 검사한다. 화면 밖 행은 누를 수 없어야 한다.
4. **입력:** 탭 1회는 생산 1회, 드래그는 생산 0회여야 한다. 경계에서 떼기, 바깥으로 이동 후 재진입, 두 손가락, 드래그 중 일시정지·회전·목록 교체를 검사한다.
5. **기존 생산:** 비용 부족, 개체 수 제한, 대기열 포화, 강화 중 생산 금지, 포탑 배치 시작·취소를 기존 결과와 비교한다.
6. **순서 보존:** 다섯 슬롯 각각에 다른 순서와 원시 레코드의 식별 바이트를 넣는다. 편집·재실행·MD1 출력과 복원 후 전체 바이트를 비교한다. 대상 레코드 이동 외의 변경은 없어야 한다.
7. **설치·해제:** 7개를 넘겨 INSTALL하고 맨 아래까지 생산한다. 중간·끝 유닛을 UNINSTALL하면 해당 행만 빠져야 한다. 재설치·재실행·MD1 복원 후 설치 여부를 확인한다. 해금됐지만 UNINSTALL한 유닛은 표시·생산되지 않아야 한다.
8. **진행 중 목록 변화:** 새 해금·설치 해제·강화 후에도 기존 순서와 유닛 이름이 유지되는지 검사한다. 잡고 있던 행이 바뀌면 액션이 취소되어야 한다.
9. **플랫폼 출력:** iPhone·iPad 시뮬레이터와 Android·Web에서 같은 저장과 스크롤 위치로 렌더한다. 실제 눌린 이름과 생성된 유닛이 같아야 한다. 디바이스 픽셀 비율에 따른 자르기 경계도 확인한다.
10. **비용 측정:** 보이는 행만 그리는 상태에서 전체 해금 전후의 draw call, 프레임 CPU 시간, 메모리 증가를 비교한다. 드래그 중 저장·텍스처 재업로드가 발생하지 않는지 계측한다.

자동 검사는 여러 저장 조건을 같은 실행에서 반복한다. 성능 측정은 플랫폼별로 한 앱씩 실행한다.
