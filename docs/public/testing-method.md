HeavyMach1에서 사용한 방법을 MachDefense에도 적용했다. 먼저 원작을 실행하는 포팅판을 만들고, 그 동작을 기준으로 소스를 재구현했다. 이어서 레벨·아이템·자금·미션 상태를 자유롭게 설정할 치트 앱을 만들게 했다. 원작을 비교할 실행본, 실제로 배포할 일반 앱, 조건을 빠르게 만드는 치트 앱을 함께 사용했다.

## 치트 앱을 만든 이유

나는 게임업계에서 개발자로 일한 경험은 없다. iOS 개발을 하며 유닛 테스트는 자주, 신속하게 실행할 수 있어야 한다고 배웠다. 수많은 게임에 치트키가 있는 이유도 생각해 봤다. 모든 무기와 강화 효과를 확인하려는데 레벨과 자금 때문에 특정 기능에 접근하지 못한다면 검사가 느려질 수밖에 없다.

그래서 Codex에게 진행도와 무관하게 게임의 기능과 상호작용을 시험할 빌드를 요구했다. 일반 앱과 치트 앱은 같은 게임 코드로 만들고 저장을 분리했다. 검사에서는 임시 저장이나 백업한 복사본을 사용했다. 내 아이폰의 실제 진행을 다른 플랫폼으로 옮기는 검사에서도 원본 저장을 먼저 보존했다.

## 생산·강화·전투·저장 검사

치트 기능으로 자금과 장비를 준비한 뒤에는 실제 구매·생산·발사·명중·승패·저장 경로를 실행했다. 자금이 충분할 때의 구매뿐 아니라 부족할 때 거절하는지도 확인했다. 저장을 다시 읽어 강화 단계가 남는지, 복원 코드로 옮겨도 같은지 검사했다.

2026년 11월 7일, 10레벨 확장과 생산 목록 스크롤 작업에서 실행한 실제 iPad 치트 앱 검사는 다음과 같다.

| 대상 | 실행한 검사 |
|---|---|
| 생산·포탑 배치·특수공격 | 280 / 120 / 100조건, 해당 검사 5.595초 |
| 기지 강화 | 120조건, 구매 552회, 외형 전환 42회 |
| 강화창의 실제 버튼 | 250행 × 2조건, 구매 225·거절 275, 디스크 재읽기 250회 |
| 무기 발사·명중 | 267정의 × 2조건, 발사 6,048회·명중 6,048회 |
| 확장 단계·복원·스크롤 | 260조건, 복원 130회, GPU 출력 133회 |

[검사 조건과 결과](../evidence/level10-hud-20261107.md)

80미션의 진행 검사에서는 승리·실패 뒤의 결과와 다음 미션, 보상, 저장을 확인했다. Android 에뮬레이터에서는 80미션에 각각 들어가 자원을 읽고 화면을 그렸다. 같은 “80미션”이라도 검사한 내용은 기록에 나눠 적었다. [캠페인 검사](../evidence/source-cheat-campaign-20261104.md) · [Android 검사](../evidence/android-native-20261106.md)

## 백그라운드 복귀 후 효과음 검사

모듈화한 앱을 직접 플레이하다가 백그라운드에서 돌아오면 음악만 나오고 포탄 발사음과 생산 완료음은 들리지 않는 것을 발견했다. 기존 검사는 효과음 재생 함수를 호출한 횟수를 세고 있었다. 실제 출력 장치가 멈췄어도 호출 횟수는 늘었다.

Codex는 효과음의 샘플 재생 위치를 읽는 검사를 추가했다. 수정 전에는 복귀 뒤 재생 위치가 0초에 멈췄다. 출력 장치의 정지·재개를 연결한 뒤에는 0.2초 대기 후 0.192~0.213초까지 진행했다. 스피커 출력음을 녹음해 원작과 비교하는 일은 별도 과제로 남았다. [재현과 수정](../evidence/effects-resume-20261105.md)

## 프레임 측정값과 의미

**프레임 검사는 p99 16.67ms, 25ms 초과는 0회였다.** 2026년 11월 7일 iPad Air 13인치(M2) 치트 앱에서, 설치 유닛 14종과 10레벨 기지·유닛·포탑을 준비한 전체 게임 세션의 측정값이다. 전투 300프레임과 같은 전투 중 HUD 스크롤 300프레임을 각각 측정했다. 디버거 없이 CADisplayLink의 연속 시각 차이를 기록했다.

60fps는 1초에 화면을 60번 갱신하는 속도다. 한 번의 간격은 약 16.67ms다. p99는 측정한 간격을 짧은 순서로 정렬했을 때 약 99% 지점의 값이다. 25ms 초과 0회는 그 구간에서 25ms보다 긴 간격을 관측하지 않았다는 뜻이다.

게임 계산과 렌더 제출의 CPU 시간 p95는 전투 5.24ms, 전투와 스크롤 5.94ms였다. 측정 구간의 게임 저장 쓰기는 0회였다. 별도 월드 검사 1,800프레임에서는 포탑 6대를 한꺼번에 만든 순간 CPU 40.85ms와 25ms 초과 1회를 기록했다. 사거리를 수정한 뒤의 재검사도 전투 299프레임·스크롤 300프레임에서 p99 16.67ms·25ms 초과 0회였으며 CPU p95는 5.31ms·5.52ms였다. [측정 장면별 기록](../evidence/level10-hud-20261107.md)

여기까지 오는 동안 기지 기관총 발사마다 오디오 컨텍스트를 해제하던 코드를 고쳤고, 메인 스레드의 오디오 세션 호출도 옮겼다. 생산 HUD에서는 비활성 유닛 위로 드래그할 때 스크롤이 취소되는 오류를 고쳤다. 기능을 빠르게 검사한 뒤 실제 시간으로 전투와 드래그를 실행해 프레임을 측정했다. 성능·음향 측정은 다른 부하 검사와 겹치지 않게 했다. [오디오 세션 수정과 계측](../evidence/audio-session-20261105.md)

## 아이폰 진행도 이전·복원 검사

빈 프로필만 검사하지 않았다. 아이폰에서 쌓은 진행·해금·강화·자금을 옮겨 코드로 복원하고, 전체 42,496바이트를 대조했다. 나는 아이폰에서 만든 코드로 아이패드 PWA를 복원해 한 판을 클리어했다. 거기서 새 코드를 만들어 아이폰에 다시 넣은 뒤 스테이지 진입까지 확인했다. [플랫폼별 복원 검사](../evidence/save-transfer-all-platforms-20261106.md)

웹 치트 앱에서는 Chrome·WebKit으로 구매·복원·전투·입력을 검사했다. 정식 앱과 운영 PWA에서는 실제 저장과 재실행을 확인했다. 구버전 PWA가 첫 갱신 때 이전 테이블을 실행하는 문제는 배포 후 검사에서 발견돼 남은 과제로 기록했다. [v0.5 배포 후 검사](../evidence/v05-release-20261107.md)

치트 앱은 내가 가진 장비와 레벨에 상관없이 기능을 꺼내 시험하게 해줬다. 내가 플레이하며 발견한 실패를 재현하고, 고친 뒤 같은 조건을 다시 검사하는 데 사용했다.
