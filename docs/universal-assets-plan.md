# 신규 버전 공용 에셋과 유니버설 앱 사전조사

2026-11-04 사용자 지시. 신규 소스 재개발판은 기기마다 별도 제품과 별도 그림을 관리하는 대신, 공용 에셋 세트로 모든 대상 기기를 지원하는 유니버설 앱을 목표로 한다. 현재 포팅판은 원본 비교를 위해 보존한다.

## 사용자 가설과 확인 범위

사용자는 HD판과 다른 판본이 서로 다른 에셋을 쓸 가능성을 제시했다. MachDefense에서 별도 HD 패키지 존재와 실제 고해상도 유닛 자원은 아직 확인되지 않았다. 확보한 세 판본은 iPhone/iPad 지원 정보를 함께 포함하며, 한 패키지 안에도 iPad·iPhone·Retina 이름의 자원이 있다. 파일 이름만으로 더 나은 원본이라고 결정하지 않는다. [판본 비교와 유닛 화질 관측](port-observations-20261104.md)을 먼저 읽는다.

## 사전조사

1. 세 판본의 전체 자원과 실행 중 선택되는 자원을 대응시킨다. 별도 HD판 존재 여부도 원본 보관 목록·패키지 정보·출처 자료에서 확인한다.
2. 유닛·부품·배경·버튼·숫자·도움말별로 원본 픽셀 크기, 알파, 내용, 크롭 영역, 피벗, 파일 해시를 비교한다. 고해상도 자원의 실제 디테일과 단순 확대본을 구분한다.
3. 원본의 iPhone/iPad·Retina 분기와 중간 합성 텍스처 크기를 확인한다. 좋은 원본 그림도 낮은 해상도로 합성한 뒤 확대하면 품질이 떨어질 수 있으므로 최종 렌더 경로까지 확인한다.
4. 공용으로 채택할 자원마다 기준 판본과 채택 이유를 명세에 남긴다. 고해상도 원본이 없으면 없는 것으로 기록한다. 이 지시는 에셋 재창작 지시가 아니다.
5. 공용 원본에서 플랫폼별 압축·패키징을 생성한다. 플랫폼 출력이 달라도 같은 원본·메타데이터를 사용하고 에셋의 수정 지점을 하나로 유지한다. GPU 텍스처 제한·메모리·알파 품질을 비교한다.

## 영문 자원 조사

신규 앱은 영어만 지원한다. 캐나다·미국 구매판의 원본 영문을 기준으로 이미지·문자열·자원 선택 절차를 조사한다. 판본별 다국어 구조는 원본 영문을 찾기 위해 분석하며 다국어 제품 기능을 추가하지 않는다. 기기 언어가 한국어여도 신규 앱의 유닛 이름·버튼·도움말·플랫폼 안내는 영어로 표시한다. [전체 판본 조사](version-audit-plan.md)에서 기준 자원을 확정한다.

## 구현 시점

자원 조사와 공용화 준비는 원작 기능 구현에 필요한 만큼 진행한다. iPhone·iPad 화면 크기에 맞춘 레이아웃 확장은 원작 기능·80개 미션 진행/저장 검사와 전체 검증을 마친 다음에 수행한다. 확장 후 배치·터치와 게임 회귀 검사를 다시 한다. [최신 작업 순서](source-reimplementation-plan.md)를 따른다.

## 구현 조건

- Apple은 하나의 iPhone/iPad 유니버설 앱을 기준으로 설계한다. 이후 요청되는 Mac·Android 등도 공용 에셋과 게임 모듈을 소비한다. 플랫폼 프로젝트 배치 규칙은 [설계](design.md)를 따른다.
- 에셋 픽셀 크기, 게임 논리 크기, 기기 화면 크기를 분리한다. 고해상도 그림으로 바꾸어도 유닛·포신·파츠 위치, 충돌 판정, 이동·탄도·사거리·속도는 원본 기준을 유지한다.
- 해상도 비율이 다른 파츠를 조립할 때 크롭·피벗·앵커를 동일한 논리 단위로 정규화한다. 차체·포탑·포신의 연결과 움직임을 원본과 대조한다.
- 화면비·안전 영역·입력 좌표는 레이아웃과 변환에서 처리한다. 기기마다 그림을 임의로 늘이거나 잘라서 맞추지 않는다. 원본 UI 보존과 전체 화면 대응을 별도 단계로 검사한다.
- 공용 에셋은 원본 패키지에서 독립된 자원으로 준비한다. 신규 앱의 빌드·실행에 IPA나 포팅 런타임이 필요하지 않아야 한다.

## 검사와 완료 조건

동일 유닛·맵을 작은 iPhone, 큰 iPhone, iPad에서 정지·이동·회전 상태로 비교한다. 원본 배율과 실제 기기 배율의 캡처, 파츠 연결, 텍스트 가독성, 가격 표시, 터치 영역을 확인한다. 확대 품질·필터·메모리·프레임을 측정한다. 추가 플랫폼은 구현될 때 같은 조건을 적용한다.

[MD-UI-01/02와 MD-ART-01](port-observations-20261104.md)의 판본 비교 결과가 채택 에셋 명세 및 구현·검사로 이어져야 한다. 원본에 없던 화면 크기 대응으로 생긴 차이는 재개발 비교표에 따로 기록한다.


## 화면 여백과 월드 확장 연구 — MD-VIEWPORT-07

2026-11-04 사용자 관측: iPhone Air는 상하에 검은 여백이 있고, iPad Air는 좌우에 미세한 검은 여백이 있다. 기존 에셋을 임의로 새로 그려 붙이지 않고, 월드를 더 보여주는 방법을 우선 조사한다. 현재 단계는 연구 계획이다. 기기 화면의 여백 픽셀 수와 실제 콘텐츠 잘림 여부는 아직 측정하지 않았다.

### 코드에서 확인한 원인과 제약

| 경로 | 현재 처리 | 확장할 때 확인할 부분 |
| --- | --- | --- |
| `GameSession::State::rebuild`, `GameSession::resize` | 논리 화면 320×480 고정, resize 구현 없음 | 화면 크기를 전달받아도 월드 표시 범위가 바뀌지 않음 |
| `MDRenderer::drawFrame` | 두 축 배율의 최솟값으로 장면을 가운데 배치 | 긴 화면의 상하, 넓은 화면의 좌우에 남는 공간 발생 |
| `World::width/height/worldToScreen/screenToWorld` | 기기 모드별 고정 크기로 카메라·입력 변환 | 가변 표시 크기와 역변환을 함께 변경해야 함 |
| `BattleGeometry` | deviceScale과 mapLength가 AI·기지 위치·무기·충돌에도 사용됨 | 화면을 채우려고 이 값을 바꾸면 전투도 달라질 수 있음 |
| `World::appendSprites` | 두 장의 배경을 정해진 월드 위치에 그림 | 현재 phone 기준 배경 전체 범위는 폭 256, 높이 1024. 무한히 넓힐 수 없음 |
| `World::touch`, `GameHUD` | 레이더·월드 터치 경계와 HUD 위치에 고정 좌표 사용 | 그리는 위치와 누르는 위치를 같은 배치 결과로 계산해야 함 |

현재 렌더러는 장면 전체를 비율에 맞춰 넣는다. 원본 장면을 확대해 잘라내는 계산은 없다. 사용자가 본 가장자리 잘림에 HUD나 다른 문제가 함께 있는지는 실제 캡처로 따로 대조한다.

HeavyMach 1의 `docs/wide-canvas-plan.md`를 참고했다. 그 프로젝트에서는 가변 캔버스를 도입한 뒤 보스가 조기에 움직이는 문제를 수정했다. MachDefense에서도 화면에 보이는 범위와 적 생성·이동·공격 조건을 분리해 검사한다. HeavyMach 1의 가로 화면 수치나 배경 확대 정책을 그대로 적용하지 않는다.

### 연구와 구현 후보

1. **실제 화면과 원작 배치를 측정한다.** iPhone Air·iPad Air에서 전체 화면, 실제 그리기 영역, 안전 영역, HUD 경계, 남는 픽셀을 기록한다. 같은 미션의 포팅판과 소스판 캡처를 비교한다. 원본 iPad용 배경·HUD가 더 넓은 내용을 담는지, 같은 그림을 크게 저장했는지도 구분한다.
2. **월드를 더 보여주는 캔버스를 시도한다.** 화면 크기를 W×H라 할 때 `s=min(W/320,H/480)`, 후보 논리 크기를 `W/s × H/s`로 잡는다. 기존 320×480을 담으면서 긴 폰에서는 세로 시야를, 더 넓은 패드에서는 가로 배치 공간을 늘린다. 이는 치트 앱에서 비교할 후보이며 최종 배율은 유닛 크기·터치 크기·실제 맵 범위를 보고 결정한다.
3. **전장 범위를 먼저 확인한다.** 80미션의 배경 범위와 충돌 지형을 대조한다. 세로 확장은 기존 맵 안에서 카메라가 더 넓게 보도록 한다. 가로는 원래 전장 폭이 좁으므로 캔버스 확대만으로 새 지형이 생기지 않는다. 기존 HUD 아래에 가려졌던 월드가 있는지 조사하고, 패드 원본 배치와 분리된 HUD 부품을 활용할 수 있는지 비교한다. 배경 그림만 늘려 통행 가능한 지형처럼 보이게 만들지 않는다. 원본 자원으로 채울 수 없는 부분은 위치와 크기를 비교안에 표시한다.
4. **표시용 크기를 전투 규칙에서 분리한다.** 카메라·투영·HUD가 소비하는 표시 크기를 별도로 둔다. 화면 크기 변경으로 deviceScale, mapLength, 난수, 생성 시점, 이동 속도, 탄도, 사거리, 피해량, 저장값을 바꾸지 않는다. 카메라 상하 한계와 파티클 제거 조건도 점검한다. 화면보다 맵이 짧을 때의 카메라 위치는 별도로 계산한다.
5. **HUD와 입력을 함께 배치한다.** 월드는 화면 전체를 사용하고 버튼·숫자·레이더는 안전 영역 안에 둔다. 원작 버튼과 게임 렌더러를 유지한다. 레이더의 카메라 위치·표시 범위, 스크롤, 포탑 설치, 특수기술 목표 선택은 같은 좌표 변환을 사용한다. 원래 세로 두 방향 지원을 유지한다.
6. **월드가 없는 화면도 따로 조사한다.** 타이틀·슬롯·미션 선택·강화·일러스트·문 전환은 월드 확장으로 해결되지 않는다. 원본 배경과 분리된 부품의 재배치를 우선 검토한다. 그림 비율을 늘이거나 새 그림을 덧붙이지 않는다. 이 화면들의 배치안도 같은 보고서에 모은다.

### 검증 순서와 완료 조건

현재 사용자가 확인 중인 원작 기능 차이를 먼저 정리한다. 이후 치트 앱에서 기존 320×480 표시와 확장 표시를 같은 저장·미션·난수로 비교하고, 검증 후 정식 앱에 반영한다. 사용자 테스트 중인 앱은 종료하거나 교체하지 않는다.

- 작은 iPhone·iPhone Air·큰 iPhone·iPad Air·큰 iPad 비율을 시뮬레이터에서 검사한다. 실제 기기에서는 Air 두 기종의 여백과 조작을 확인한다. 세로 두 방향에서 HUD·모서리·안전 영역을 검사한다.
- 맵 하단·중간·상단에서 월드 표시와 카메라 한계를 확인한다. 화면 확장이 적의 생성·이동·공격을 앞당기거나 지형 판정을 바꾸지 않아야 한다.
- 같은 월드 좌표 입력을 재생해 생산 비용·생성 순서·공격·피해·클리어·저장값을 비교한다. 화면 크기만 다른 상태에서 발생하는 차이를 찾는다.
- 화면 가장자리에서 포탑 설치, 설치 취소, 특수기술, 레이더 이동, 생산·강화·일시정지 버튼을 누른다. 미션 3 구멍 지형의 설치 문제 `MD-TERRAIN-06`은 포팅판 대조 결과를 기준으로 별도 검사한다.
- 같은 교전 장면의 프레임 시간·메모리·음향 재생을 기존 측정과 비교한다. 표시 범위 확장에 따른 그리기 비용과 실제 전투 처리 비용을 구분한다.
- 산출물은 화면별 전후 비교, 원본 에셋 선택 근거, 좌표 변환 검사, 전투 비교, 성능 결과다. [기존 통합 보고서](editorial/machdefense-report.md)에 연결한다.
